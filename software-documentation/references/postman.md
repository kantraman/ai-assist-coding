# Postman collections

A Postman collection is useful only if it matches the real API and runs out of the box. Generate it from an OpenAPI spec instead of hand-writing JSON, so the collection, the API reference and the code share one source of truth.

## 1. Workflow

1. Locate an existing OpenAPI 3.x file (`openapi.json|yaml`, `swagger.json`, a `/docs` or `/openapi.json` export, or one generated by the framework). Swagger 2.0 must be converted to OpenAPI 3 first.
2. No spec? Write one from the code (section 2).
3. Run `scripts/build_postman_collection.py` (section 3).
4. Read the "documentation gaps" warnings it prints. Fix the spec where you can verify the answer from code; otherwise record the gap as an open question.
5. Add a workflow/smoke folder if the API has multi-step flows (section 5).
6. Save the collection, environment, and spec together under `docs/postman/` and `docs/openapi.*`.

## 2. Producing the OpenAPI spec when none exists

Build it from what the code actually does, not from memory:

- Routes/controllers -> `paths` and methods.
- Request validators/DTOs/schemas -> `requestBody` and `parameters` with types, required flags, constraints, enums.
- Response serializers/types and tests/fixtures -> `responses`, with real `examples`.
- Auth middleware -> `components.securitySchemes` and `security`; mark public routes with `security: []`.
- Error handlers -> shared error schema in `components.schemas`, referenced from 400/401/403/404/409/429 responses.
- Add `tags` per resource, a `summary` for every operation, and a one-line `description` where behaviour is non-obvious.
- Put explicit `example` values on request bodies and success responses; the generator uses them verbatim.

Use JSON if PyYAML may be unavailable; YAML works when PyYAML is installed.

If part of the API cannot be determined from the sources, leave it out of the spec and list it as an open question. A collection with a wrong request is worse than one with a missing request.

## 3. Running the generator

```bash
python scripts/build_postman_collection.py docs/openapi.json \
  --out-dir docs/postman \
  --name "Shop API" \
  --env-name Staging \
  --base-url https://staging.shop.example.com/v1 \
  --max-ms 2000
```

| Option | Meaning |
|---|---|
| `spec` | OpenAPI 3.x file (.json, or .yaml/.yml with PyYAML) |
| `--out-dir` | Output folder (created if needed) |
| `--name` | Collection name; defaults to `info.title` |
| `--base-url` | Overrides `servers[0].url` |
| `--env-name` | Suffix for the environment name (Local, Staging, Production) |
| `--max-ms` | Response-time assertion threshold |

Run it once per environment if the team wants separate environment files (change `--base-url` and `--env-name`; the collection file is identical and can be reused).

## 4. What the generator produces

- **Collection (v2.1)** with folders per tag, request names from summaries, descriptions, saved response examples (success and error) taken from the spec.
- **Variables:** `{{baseUrl}}` plus auth variables (`{{token}}`, `{{username}}`/`{{password}}`, or `{{apiKey}}`) depending on the security scheme. Path parameters are Postman path variables (`:orderId`) with example values.
- **Auth:** set once at collection level from the global `security`; overridden per request where the spec differs; `noauth` for public routes.
- **Tests on every request:** expected 2xx status, response time, JSON content type, presence of required response fields. If a success response contains `token`, `accessToken`, `access_token` or `jwt`, the test stores it in `{{token}}`, so running the login request once authenticates the rest.
- **Environment file** with `baseUrl` and secret-typed auth variables left blank.

Query parameters that are optional are included but disabled; required ones are enabled.

## 5. After generating: improve and verify

**Verify:** the script validates structure and prints a summary. Also confirm by reading the JSON that: the folder list matches the API's resource list, a couple of requests have the right URL, body and auth, and the login request exists if auth is required.

**Add workflow chaining when the API has dependent calls** (create -> read -> update -> delete). Put these in an extra folder, e.g. "Workflows / Order lifecycle", and pass IDs between requests with a test script:

```javascript
// In the "Create order" request, Tests tab
const body = pm.response.json();
pm.collectionVariables.set("orderId", body.id);
```
```
// In following requests, use {{orderId}} in the URL: {{baseUrl}}/orders/{{orderId}}
```

Edit the generated JSON programmatically (load, append an `item` folder, write back) rather than by hand when adding these; keep the generator's output untouched otherwise so it can be regenerated.

**Negative-case requests** for the main flows are valuable (missing field, wrong role, unknown ID) and double as executable documentation of the error catalogue. Add them when the API reference lists those errors.

**Pre-request scripts** only when needed (timestamps, signatures, random unique emails): `pm.variables.set("email", `qa+${Date.now()}@example.com`)`.

## 6. Handing it to the team

Include these steps in the engineering docs (adapt names):

1. In Postman choose **Import** and select the collection and environment JSON files.
2. Select the environment in the top-right dropdown.
3. Fill in the credentials or key in the environment's **Current value** column.
4. Run the **Log in** request (if present); `{{token}}` is saved automatically.
5. Run any request, or use **Run collection** to execute everything and see test results.

Command-line / CI option (when Node is available to the team):

```bash
npx newman run docs/postman/shop-api.postman_collection.json \
  -e docs/postman/shop-api.postman_environment.json
```

Add a note on which environments are safe to run the full collection against: it contains DELETE and POST requests, so never point it at production data without care.

## 7. Hygiene rules

- No real secrets, tokens, or production credentials in either file. Secret variables ship empty.
- Do not hard-code environment URLs in requests; always `{{baseUrl}}`.
- Regenerate from the spec whenever the API changes, and note this in the changelog. Do not maintain the collection and spec independently.
- Name requests by what they do ("Create order"), not by URL.
- State in the docs which version of the API the collection matches.
